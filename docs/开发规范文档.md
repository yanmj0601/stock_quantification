# EvoQuant 开发规范

## 1. 环境与目录职责

- `src/evoquant/domain.py`：无基础设施依赖的领域类型和枚举。
- `src/evoquant/providers/`：外部行情适配，统一返回 Provider 数据类。
- `src/evoquant/services/`：业务规则、数据库读写和计算。
- `src/evoquant/api.py`：Pydantic 请求模型、HTTP 映射和依赖组装。
- `frontend/src/pages/`：页面；`frontend/src/api.ts`：统一 HTTP 客户端。
- `tests/`：pytest 测试；`docs/`：现行设计与生成契约。

开发安装：`uv sync --extra dev`；前端安装：`cd frontend && npm install`。需要运行 `scratch/` 中的 NAS SSH/SFTP 工具时使用 `uv run --extra ops python <脚本>`，并通过环境变量提供主机和凭据。

## 2. 命名和代码风格

- 面向团队和用户阅读的 Markdown 文档、手工维护的 SQL 脚本使用清晰的中文文件名，例如 `产品需求文档.md`、`sql/初始化.sql`。
- 工具链约定或机器读取的文件保留标准名称，例如 `README.md`、`Dockerfile`、`pyproject.toml`、`package.json`、`openapi.json`；Python、TypeScript 源文件及模块路径也遵循对应语言和生态的英文命名约定，避免破坏导入、构建和部署。
- 项目内新增或修改的代码注释、模块文档字符串使用中文。标识符、协议名、API 路径、SQL 关键字及无法准确翻译的技术名词可以保留英文。
- 注释解释业务原因、边界或不直观的实现选择，不逐行复述代码；代码变化后必须同步更新或删除失效注释。
- Python 使用 PEP 8：模块、函数和变量用 `snake_case`，类用 `PascalCase`，常量用 `UPPER_SNAKE_CASE`。公共函数和服务方法写类型标注。
- TypeScript 组件和类型用 `PascalCase`，函数和变量用 `camelCase`，页面组件默认导出；共享请求统一经过 `api.ts`。
- 数据库表和字段用 `snake_case`；业务 ID 使用 `new_id("前缀")`，不要依赖数据库自增。
- API 路径使用小写复数名词和连字符，如 `/api/paper/accounts`、`/api/data-sync/bar-jobs`；动作路由只用于 approve、cancel、submit、retry 等状态转换。
- 保持文件职责单一，优先复用既有 service/provider 模式；不要在页面复制后端规则。

## 3. 日志规范

- 使用 `logging.getLogger(__name__)` 或统一的 `evoquant` logger，禁止用 `print` 记录服务运行信息。
- 正常生命周期和可恢复业务事件用 `INFO`，外部数据退化用 `WARNING`，请求无法完成且需排查时用 `ERROR/exception`。
- 异常日志包含任务 ID、市场、provider 等定位字段；使用参数化日志，避免拼接大型对象。
- 不记录数据库连接串、API key、密码、完整个人数据或不受限的第三方响应。
- API 的预期 4xx 不需要堆栈；后台线程未预期异常使用 `LOGGER.exception` 保留堆栈。

## 4. 异常处理

- 领域/service 对无效输入抛 `ValueError`，非法状态转换或风控阻断抛 `RuntimeError`，资源不存在抛 `KeyError`。
- API 层把 `KeyError` 映射为 404，把可预期 `ValueError/RuntimeError` 映射为 400；Pydantic 校验失败由 FastAPI 返回 422。
- 不使用宽泛 `except Exception: pass`。批量行情同步允许捕获单标的异常，但必须把 symbol 和原因写入任务 failures。
- 数据库写操作放在 `store.connection()` 中；异常必须回滚。跨多个连接的业务动作当前不是原子事务，修改时需显式评估一致性。
- 外部请求必须设置超时；只有明确可重试的限流或瞬时错误才重试，并设置次数上限。

## 5. 数据库规范

- 运行时只支持 PostgreSQL。新增/修改表时同步修改代码 DDL、[初始化 SQL](sql/初始化.sql) 和 [数据库设计](数据库设计文档.md)。
- SQL 参数使用 `?` 占位，由 wrapper 转换为 psycopg2 格式；不要拼接用户输入、表名或字段名。
- JSON 字段通过 `dumps/loads` 读写；日期和时间沿用 ISO 8601 字符串约定。
- 常用过滤或排序路径新增索引前，先用实际查询说明收益；将索引写入代码 DDL和初始化 SQL。
- 测试必须显式配置 `EVOQUANT_TEST_DB_URL`。fixture 为每个测试创建随机 schema，禁止指向生产数据库。

## 6. API 与前端契约

- 新路由应定义明确 Pydantic 请求模型、成功状态码及可预期错误映射。
- 修改路由、字段、枚举或状态码时，同步更新前端调用、[API 文档](接口设计文档.md) 和 OpenAPI：

```bash
uv run python tools/export_openapi.py
uv run python tools/export_openapi.py --check
```

- 前端必须处理非 2xx 响应并显示后端 `detail`；不要吞掉网络异常。
- 改页面后至少运行 `npm run typecheck` 和 `npm run build`。

## 7. 测试规范

- 修复缺陷先写可重现的失败测试，再做最小修复；测试应验证可观察行为，不绑定内部实现。
- 纯计算尽量不依赖数据库；集成测试使用临时 schema，不能创建、清空或删除共享数据库。
- 默认验证命令：

```bash
EVOQUANT_TEST_DB_URL='postgresql://localhost:5432/evoquant_test' uv run --extra dev pytest -q
cd frontend && npm run typecheck && npm run build
uv run python tools/export_openapi.py --check
git diff --check
```

- 外部行情测试使用固定 fixture/provider，常规测试不得依赖公网或真实 API key。

## 8. Git 提交与评审

- 分支默认使用 `codex/<主题>` 或团队约定的 feature/fix 分支，不直接在共享主分支堆叠未验证改动。
- 提交消息使用 `type: 简短祈使描述`，推荐类型：`feat`、`fix`、`docs`、`test`、`refactor`、`chore`。
- 每个提交保持一个可解释目的；相关代码、测试和文档放在同一提交，不提交 `.env`、数据库文件、构建产物或凭据。
- PR 描述说明触发场景、改动后的行为、验证命令和已知限制。评审重点检查人工审批/真实交易边界、数据库破坏性操作、外部调用和文档契约。

## 9. 文档维护

| 变化 | 必须同步的文档 |
|---|---|
| 用户流程、业务规则、产品范围 | `产品需求文档.md`、`平台使用指南.md` |
| 技术选型、模块、部署或数据流 | `系统架构设计文档.md` |
| 表、字段、约束或索引 | `数据库设计文档.md`、`sql/初始化.sql` |
| API 路由、请求、响应、状态码 | `接口设计文档.md`、`openapi.json` |
| 开发流程或工具链 | `开发规范文档.md`、根 `README.md` |

历史设计稿用于追溯，不回写为当前事实；现行文档有冲突时，以代码和自动生成契约核验后修正文档或实现。
